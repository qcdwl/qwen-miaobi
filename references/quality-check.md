# 发布前质量检查

内部执行，不默认把自检表输出给读者。需要修改的问题直接改好。按下面的优先级做两轮检查。

## 第一轮：硬性问题（有问题就不交付为可直接发布稿）

| 检查项 | 验收标准 | 修正方法 |
| --- | --- | --- |
| 第一人称经历 | 每个实测、领取、收益、反馈均有用户材料 | 删去或改成明确来源/示例 |
| 时效性 | 功能、版本、活动、佣金、热搜都有可信当期依据 | 删除、标待核实或条件化，不只补免责句 |
| 数字口径 | 指标、日期、主体、单位、适用范围一致 | 不混用热度/播放、预估/实际 |
| 产品/版本 | 官方、第三方、客户端与账号类型区分正确 | 明确身份，复核系统与发行包 |
| 安装与教程 | 步骤来自真实资料或明确任务示例 | 不编UI，不默认跳过系统安全 |
| 推广链接 | 与使用者给出的完整原始字符串一致 | 逐字符比较；缺失用指定占位 |
| 关系披露 | 实际商业关系清楚，符合平台规则 | 入口附近加入真实披露；未知则提醒补充 |
| 合规与隐私 | 无刷量、虚假注册、规避风控或敏感信息泄漏 | 删除违规内容，改为真实用途 |
| 原创 | 未复制同行全文、独特句序或近义洗稿 | 换场景与论证，必要引用注明来源 |

遇到关键事实冲突，不能静默修正成更有利的宣传说法；按来源范围写明冲突并请求确认。若网络或来源不足，仍可输出已知部分，但必须将未确认事项列为发布前核对，避免误导标题。

## 第二轮：写作质量（内部人工式通读）

每项评估「通过 / 需修改」，不制造虚假的AI味检测百分比。

1. 标题与正文是否解决同一个问题？第一段能否直接进入主题？
2. 读者是否拿到具体信息或操作，而不是一堆评价？能否删掉任何空段？
3. 有没有凭空出现的「朋友问我」「我刚试过」或为了真人感刻意错字？
4. 句子是否自然完整？段落长短是否随语义变化？是否全篇机械单句换行？
5. 结构是否符合平台和本次需求？有没有固定的三大点、万能开头、过多标题和加粗？
6. 个人观点是否有理由与边界？是判断还是冒充事实？
7. 实际场景与产品是否真正相关？链接是否出现在读者需要的位置？
8. 结尾能否直接停住？是否又复述功能、强行感悟时代或喊关注？
9. 连续文章有没有新增信息？如无法读取历史稿，不假装做过重复度对照。
10. 按用户要求输出标题/正文或局部改写了吗？是否多出了无关自评或创作说明？

## 无法完全核验的处理

默认只交付标题和正文。若缺资料导致重要断言不能确认，正文以已知事实或明确假设写；最后另列「发布前核对」说明未验证的内容、来源缺口、链接占位。必要时给可查证的官方入口。不要承诺未来会后台完成，也不要把一份未核实草稿称作可以直接发布的活动教程。
